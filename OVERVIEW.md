# OVERVIEW.md

Current architecture of archstaller. Kept in sync with the repo by rule (see `AGENTS.md` and `CLAUDE.md`).

## What it is

An Arch Linux installer that boots without any Linux kernel. Our own single-purpose boot loader (`boot/`, BIOS + UEFI) loads a custom
`no_std` Rust mini-kernel that installs Arch onto disk: partitions, downloads and verifies packages over
HTTPS, writes the filesystem, and hands off to a first-boot service that runs real pacman/systemd steps
that need a running Linux.

## Boot/install flow

1. **Boot loader** (`boot/uefi` for UEFI, `boot/bios-s1` + `boot/bios` for BIOS, both finishing in `crates/loadcore`)
   finds the payload bundle (`payload.bin`: the kernel image plus modules `config.bin`, `keyring.bin`,
   `tiny-init`, `bootx64.efi`, `bios-boot`, each deflated; layout in `crates/bootinfo`), unpacks it, builds
   page tables (direct map at `0xffff800000000000`, kernel at `0xffffffff80000000`), and enters the kernel with
   a `bootinfo::BootInfo` (memory map, framebuffer, modules) in `rdi`. No config, no menu, no CLI.
2. **kernel** (`kernel/src/main.rs`, `install.rs`) runs, single core, polling only:
   - enumerates disks/NICs via `crates/drivers::probe_all()` (PCI scan) and prints every storage and network PCI device (`pci bus:dev.fn vendor:device class`) so an unsupported controller is visible. With the `usb-tethering` kernel
     feature it also brings up a tethered phone (iPhone via `imobiledevice::tether()`, Android via
     `usbnet::probe()`) and adds it as one more NIC when no wired NIC has link.
   - selects the target disk per `Config.disk` (serial match, or `auto_largest`); writes nothing until
     this succeeds.
   - DHCP, then downloads `core.db`/`extra.db` over HTTPS (`crates/net`).
   - resolves packages (`crates/pkg`): pacman-compatible `vercmp`, versioned deps, soname provides,
     groups, repo priority, conflicts.
   - refuses a disk too small for the resolved packages (download + installed size, plus 10% and 1 GiB) before
     anything is written.
   - partitions (`crates/disk`): GPT + protective MBR, BIOS boot partition, ESP (FAT32, `/boot`; grown past `esp_mib` when the disk's sectors need it, e.g. about 257 MiB with 4 KiB sectors), root.
   - writes root using the configured filesystem writer (`ext4` via `crates/ext4w`, `btrfs` via `crates/btrfsw`, `xfs` via `crates/xfsw`, or `f2fs` via `crates/f2fsw`), write-once, with a random UUID; only the selected filesystem engine is compiled into the installer kernel per build to avoid ISO bloat. Ext4 includes an internal jbd2 journal and random directory hash seed; Btrfs sets up `@` and `@home` subvolumes with linear chunk trees; XFS V5 sets up AG 0 with Castagnoli CRC32C and shortform/block directories; F2FS formats checkpoint, SIT, NAT, and SSA segments with TEA directory hashing.
   - streams each package into `/var/cache/pacman/pkg` on the target, verifying SHA-256 and PGP signature
     (`crates/pgp-lite` + `keyring.bin`) before extracting.
   - writes `/etc` (fstab, hostname, locale, mirrorlist, a DHCP `.network` file for wired interfaces when
     `systemd-networkd` is enabled, ...), builds an initramfs (`crates/initrd` +
     `tiny-init`), installs the boot loader on the target (UEFI: our `BOOTX64.EFI` + `archstaller.cfg` on the ESP; BIOS: stage 1 in the MBR, stage 2 in the BIOS boot partition, told where `vmlinuz-linux` and the initramfs lie). That first-boot loader only starts the Arch kernel (UEFI: `LoadImage` of the EFI-stub `vmlinuz` with the command line and an initrd `LoadFile2`; BIOS: Linux 64-bit boot protocol).
    - dumps the captured boot/install log (`logdump.rs`) to a USB flash drive on the way out, on both success and failure, immediately before the reboot: it matches the boot disk's fingerprint (recorded by the loader), finds the Ventoy data partition (exFAT with a `ventoy` directory) and appends `archstaller-log.txt` through `crates/exfatw`; any other medium gets one skip line and is left untouched. Floppy disks (<= 2880 sectors) and optical media (CD/DVD/Blu-ray, sector size 2048) are guarded against log and error dumping.
    - reboots.
3. **First boot** (`firstboot/`): `archstaller-firstboot.target`/`.service` runs `pacman-key --init/
   --populate`, `pacman -U --overwrite '*'` on the cached packages (runs real scriptlets/hooks, writes
   the local pacman DB), creates users, clones/downloads GitHub dotfiles for configured users and links configurations using GNU Stow (`stow -t ~`), exports `ARCHSTALLER_OVERLAY` and `ARCHSTALLER_DATA` for custom scripts, executes `pre-service` scripts, installs custom systemd units, enables services (with `systemd-resolved`, points `/etc/resolv.conf` at its stub), executes `post-service` scripts, builds the real
   initramfs (without the `kms` hook, so a failing GPU driver cannot block the boot), replaces our loader with GRUB (`grub-install` for UEFI removable path + BIOS, hand-written `grub.cfg` that finds `/boot` by its file system UUID and starts the `linux` kernel, or the first other kernel package when `linux` is not installed (the installer picks the same one for the first boot and takes only that kernel's modules); `grub` must be in `packages`), removes the first-boot loader files from the ESP, reboots into the installed system.

## Config (`configs/config.toml` -> `config.bin`)

Evaluated on the build host by `xtask` (`toml`), serialized with `postcard`, embedded as the `config.bin` payload module.
A config defines: `system` (`hostname`, `timezone`, `locale`, `keymap`, `root_password_hash`), `install` (`disk` selector + `esp_mib`, `mirrors`, `dry_run`), `packages` (`explicit`, `providers` as a dependency -> package table, written sorted; `aur`: pinned AUR recipes with name, pkgbase, 40-hex commit, SHA-256 of the reviewed tree and the official packages they need; the INSTALLED system builds them at its first boot, nothing AUR-related is in the ISO; needs a network service in `first_boot.services`; see `plans-implement/aur.md`), `users` (`password_hash` is a crypt hash (yescrypt, SHA-512, etc.), never plaintext; names must be unique; optional `dotfiles` configures a GitHub repository to clone into `~/dotfiles` with optional GNU Stow linking), `first_boot` (`services`, `custom_services`: inline or local unit files, targeted at root for `/etc/systemd/system` or a user from `users` for `~/.config/systemd/user`, `kernel_params`, `user_files`, `user_archives` (supports .tar.zst, .tar.xz, .tar.gz, .tar.bz2, and .zip up to 256 MiB from remote HTTPS URL, local file embedded into ISO, or partition UUID with path defaulting to `home.tar.zst`), `system_files` (path, mode, file or directory content written to root and preserved in first-boot overlay), `scripts`: built-in id, local file embedded at build time, or https URL pinned by sha256; optional `phase` ("pre-service" or "post-service"); run as root in order during first boot by `firstboot.sh`) and the host-only `build` (`profile`, `tethering`, `installer_drivers`; never serialized into the ISO).
`crates/hostcfg/src/asconfig.rs` deserializes it with `deny_unknown_fields` everywhere and a full error path (`system.hostname: ...`, list positions from 1), then normalizes it into `config::Config` (`config/src/lib.rs`, the installer part) and `HostConfig` (`crates/hostcfg/src/host.rs`). `xtask` validates values strictly (they end up in shell-read files, unit files, boot loader config): the domain rules stay in `Config::validate`, `HostConfig::validate` and `scripts::validate`. `config.bin` is serialized with `postcard` for the kernel contract.

## Trust model

- Keyring blob (`boot/keyring.bin`) is derived at build time from a pinned `archlinux-keyring` package
  (`xtask/keyring.pin`, sha256-checked), reduced to fingerprint + pubkey + expiry per packager key that
  has web-of-trust certification from the main Arch signing keys (`xtask/src/keyring.rs`). The host-side
  GnuPG home is mode `0700` on Unix; on Windows it uses the inherited filesystem ACL.
- Package signatures come from the sync DB's `%PGPSIG%` field, verified against that blob
  (`crates/pgp-lite`) before extraction; SHA-256 from `%SHA256SUM%` is checked too.
- Sync databases themselves are not signed; their integrity relies on HTTPS.
- `cargo xtask update-keyring` moves the pin forward and rebuilds the blob.
- First boot's `pacman -U` re-verifies everything with real GnuPG as a backstop.

## ISO layout (assembled by `xtask/src/iso.rs`)

ISO9660 (via `xorriso`, hybrid El Torito BIOS + UEFI, also bootable when written to a USB stick) with just two
files: `boot/bios.img` (stage 1 padded to 2048 bytes, then stage 2) and `boot/efi.img` (a FAT12 image with
`EFI/BOOT/BOOTX64.EFI` and `payload.bin`). The BIOS stages read the payload straight out of `efi.img` inside
the ISO: after `xorriso` finishes, `xtask` (`bios.rs`) finds both files in the ISO 9660 tree and patches stage 1
(into the boot image and the hybrid MBR) and stage 2's header with their byte offsets. The payload is always compressed. About 0.77 MiB total; see `sizes.md`.

## Floppy layout (assembled by `xtask/src/floppy.rs`)

A standard 1.44 MB (1,474,560 byte) raw bootable diskette image (`target/archstaller-floppy.img`):
- LBA 0 (512 B): Stage 1 boot sector (`boot/bios-s1`), configured for 512-byte sectors and drive `0x00`.
- LBA 1..39 (19,968 B): Stage 2 binary (`boot/bios`), loaded by stage 1 via legacy CHS reads.
- LBA 40..1199 (~594 KiB): Payload bundle (`payload.bin` with deflated kernel, `config.bin`, `keyring.bin`, etc.), loaded into RAM (`0x1000000`) by Stage 2 via CHS reads.
Total image size is exactly 1,440 KiB (2,880 sectors); the compressed installer and stages occupy ~615 KiB (~41.7% of the diskette), leaving over 850 KiB free. Floppy images explicitly disallow embedded `user_archives` and `system_files`.

## Raspberry Pi layout (assembled by `xtask/src/rpi.rs`)

A standard 32 MiB (33,554,432 byte) bootable FAT32 image (`target/archstaller-rpi.img`) ready for SD cards or USB drives:
- Filesystem: FAT32 formatted with volume label `ARCHBOOT` (via `mformat`).
- `kernel8.img`: Bare-metal 64-bit kernel binary (`kernel-rpi`, AArch64).
- `config.txt`: Boot firmware configuration (`arm_64bit=1`, `enable_uart=1`, `uart_2ndstage=1`, `dtoverlay=disable-bt`).
- `cmdline.txt`: Serial & kernel boot parameters (`console=serial0,115200 console=tty1 rootwait`).
- `config.bin`: Postcard-serialized installation configuration.
Directly flashable to SD cards (`/dev/mmcblk*`) or USB drives via the GUI physical media writer or `cargo xtask rpi-build`.

## Testing

- `cargo xtask test [--qemu|--all]`: runs all unit tests across the workspace on the host (`cargo test --workspace`), and with `--qemu` or `--all` additionally runs the automated QEMU suites (`linux-test`, `floppy-test`, `rpi-test`).
- Host unit tests per crate (`cargo test -p <crate>` or `cargo test --workspace`): bare-metal and OS crates (`kernel`, `boot-uefi`, `boot-bios`, `tiny-init`) use a dual-mode pattern (`#![cfg_attr(not(test), no_std)]`, host test harness) to test pure parsing, configuration generation, header decoding, and speed math without needing QEMU, alongside library crate tests (`vercmp` vs `/usr/bin/vercmp`, resolution vs `pacman -Sp`, `ext4w` images vs `e2fsck`/`debugfs`, GPT vs `sfdisk`/`fdisk`, FAT32 vs `fsck.fat`).
- `cargo xtask linux-test`: boots the host Linux kernel with our initramfs + an ext4w-built root.
- `cargo xtask e2e [--uefi] [--disk virtio|ahci|nvme|ide] [--nic ...] [--config FILE]` (`ide` runs on QEMU's i440fx board with a PIIX IDE controller): full install in QEMU onto a blank
  disk, then boots the result twice.
- `cargo xtask run --usb`: adds `qemu-xhci` + `usb-storage` and builds the `usb-selftest` kernel, which enumerates the USB device and runs a SCSI INQUIRY over bulk endpoints.
- `cargo xtask size [--profile super-small|large] [--limit BYTES]`: ISO content breakdown + size budget check.
- `cargo xtask check-presets`: resolves every preset against local pacman sync DBs.
- `cargo xtask rpi-build [--config FILE] [--out FILE] [--progress json]`: builds bootable 32 MiB FAT32 image for Raspberry Pi.
- `cargo xtask rpi-test [raspi3b|virt]`: automated QEMU bare-metal test verifying EL3->EL1 exception level drop, CPU MIDR detection, system timer, PL011 UART console initialization and boot success.
- `cargo xtask floppy-test`: automated QEMU boot test from 1.44 MB floppy image (`-fda target/archstaller-floppy.img`), verifying stage 1 CHS reads, stage 2 CHS payload load, long mode switch, and kernel console banner.

## Debug output

Driver and network tracing (`usb:`, `net:`, `r8169:` trace lines, ARP traces, idle-tick info, per-frame logs) is behind the
kernel feature `debug` (`hal::DEBUG`, `hal::log!`), set by `cargo xtask build --debug` (also `run`, `presets`, `e2e`) and
always on for a dry-run config such as `configs/tester.toml`. In a normal build `hal::log!` compiles to nothing. Always on:
`hal::info!` messages (failures such as a failed DNS lookup or USB step, an address conflict, the DHCP lease) and the
install progress the user sees (memory and heap size, disks, resolved package count and size, `[i/n] name version (KiB) P%`
per package, a download summary).

Everything printed also lands in an in-RAM ring (`kernel/src/logbuf.rs`, `crates/logring`; 128 KiB, oldest bytes
dropped once full). At the end of the install flow, on success and on failure, `kernel/src/logdump.rs` writes that
capture to a USB flash drive so a failed run can be read afterwards without a serial cable. It is deliberately narrow:
the loader records a fingerprint of the disk it booted from (`bootinfo::BootMedium`; UEFI through Block I/O, BIOS
through a real-mode INT 13h read in `boot/bios/src/entry.s`), and the kernel matches it against every enumerated disk,
walks that disk's partition table (GPT or MBR), and only appends `archstaller-log.txt` to a Ventoy data partition (exFAT
with a `ventoy` directory) using `crates/exfatw`. Every other case prints one `log dump skipped: ...` line and leaves the
disks untouched, and a rerun never overwrites an existing log.

## USB tethering (optional)

Off in a plain build; build with `--features usb-tethering` on the kernel (`cargo xtask build --tethering`). `cargo xtask presets` turns it on for every preset unless given `--no-tethering`.
`kernel/src/main.rs` (`usb_tether`) runs after `probe_all()`, but only when no wired NIC has link. It scans
all xHCI controllers once (`usb::Scan`: waits up to 2.5 s for ports to report a connection, enumerates every
configuration of every device), then:
- If an Apple device with the mux interface is present, it runs the iPhone flow below and stops.
- Otherwise `usbnet::probe()` looks for an Android tethering function or a USB Ethernet dongle.
- If a phone-like device is attached but none tethers (an Android in file-transfer mode; devices that only
  expose storage, HID, hub, audio, video or Bluetooth interfaces do not count), it prints a hint and re-scans
  every 3 s, six times, because the phone re-enumerates once the user switches tethering on.
`install::run` uses the first NIC with link, so a wired NIC wins if present. Every step logs a `usb:` line.

### iPhone (verified on real hardware)

1. `Muxer::find` takes the phone's USB configuration that has both the mux interface (ff/fe/02) and the
   tethering interface (ff/fd/01).
2. `mux.rs` does the usbmux version handshake (v1 then v2 header) and opens a TCP-like connection to
   lockdownd (port 62078).
3. `lockdown.rs`: QueryType, GetValue `DevicePublicKey`, then `Pair` with a freshly generated pair record. The
   user taps "Trust" (and enters the passcode); the request is repeated while the phone answers
   "dialog pending"/"password protected", for up to 120 s. A successful reply may carry only an `EscrowBag`
   and no `Result` key. The record is not persisted.
4. `netdev.rs`: `SET_INTERFACE` to the tethering interface's data alternate setting, vendor request 0x00 for the
   MAC, vendor request 0x45 until the carrier is up (hotspot on), then bulk IN/OUT carry plain Ethernet
   frames (received frames have 2 padding bytes). `crates/net` is untouched.

### Android phones and USB Ethernet dongles (`crates/usbnet`)

`usbnet::probe` takes the first non-Apple device with one of four network functions and brings it up as a NIC
(a known vendor chip is preferred over class functions the same device also offers):
- **RNDIS** (control interface class e0/01/03, 02/02/ff or ef/04/01 plus a CDC data interface; what nearly all
  Android phones use): INITIALIZE, QUERY the permanent MAC (with a 48-byte information buffer, like Linux's
  `rndis_host`; devices reject an empty one), SET the packet filter, then bulk transfers wrap each Ethernet frame
  in a 44-byte RNDIS packet header (several may share one transfer).
- **CDC-ECM** (02/06/00): MAC from the Ethernet functional descriptor's string, packet filter request (a stall is
  tolerated), plain frames.
- **CDC-NCM** (02/0d/00, `ncm.rs`): GET_NTB_PARAMETERS, MAC as for ECM, frames in 16-bit NCM Transfer Blocks
  (one datagram per block on transmit, any number on receive). NTB32 and NCM1 (datagram CRC) are not handled.
- **ASIX AX88179** (`ax88179.rs`, vendor-specific interface ff/ff/00; the Axagon ADE-SG and other
  AX88179-compatible gigabit dongles, matched by USB id; verified on a real ADE-SG): PHY power-cycle and clock select, MAC read, RX/TX
  control, auto-negotiation restart, wait for link (up to 15 s, so a cable must be plugged in), then the RX queue
  and medium mode follow the negotiated speed. Transmit frames carry an 8-byte header; received transfers hold
  several packets plus a trailing packet table. Other vendor-specific chips (ASIX AX88772, Realtek RTL8152/8153,
  ...) are not supported unless they also offer a CDC configuration, which the scan finds because it looks at
  every configuration of every device.
There is no pairing for any of them: for a phone the user switches "USB tethering" on in the settings and the
phone runs DHCP on the link; a dongle just needs a cable to a router.

### Testing

`cargo xtask presets` builds `target/isos/archstaller-<preset>.iso` for all nine presets (the tester included). The xHCI driver and the whole Android path run in QEMU: `cargo xtask run --usb` (`qemu-xhci` + `usb-storage`,
bulk-only INQUIRY) and `cargo xtask run --selftest --headless --nic usb-rndis` (QEMU's `usb-net` offers RNDIS in
configuration 2 and ECM in configuration 1; the selftest then does DHCP, an HTTPS download and 1 MB HTTP
transfers over the USB NIC). `--nic none` removes all NICs. The iPhone parts need a real phone: the usbmux and
lockdown framing has byte-level unit tests, the rest was verified by hand on hardware. `QEMU_EXTRA` adds raw
QEMU arguments to `xtask run` (e.g. `-trace usb_*`).

## Out of scope

Wi-Fi, USB devices other than tethering phones and Ethernet dongles, SMP, Secure Boot, an interactive
installer-kernel UI, filesystems other than the supported big four (`ext4`, `btrfs`, `xfs`, `f2fs`), architectures other than x86_64. A host desktop GUI is
implemented in `gui/` (GTK4; it copies to Ventoy or, opt-in, flashes whole physical media — USB drives, optical discs via xorriso, 1.44 MB floppy diskettes, and Raspberry Pi SD/USB cards — through a unified media target selector and UDisks2). Specs exist for Wi-Fi in `plans-implement/wifi.md`. For Raspberry Pi (ARM/AArch64), bare-metal kernel, FAT32 boot image generation, GUI build/flash integration, and QEMU E2E test are implemented in `kernel-rpi`, `crates/hal/src/aarch64.rs`, `xtask/src/rpi.rs`, and `gui/` (`cargo xtask rpi-build`, `rpi-run`, `rpi-test`); full spec and roadmap in `plans-implement/raspberry-pi.md`.
